# Ставим поллер: как подключить Claude Code к этому харнессу

Ниже промпт, который делает всю установку. Вставить его в свежую сессию Claude
Code целиком, подставив пять значений из `.env` того стенда, к которому
подключаемся. Больше ничего готовить не надо.

Что получится: часы, расписание и пределы остаются на стенде, а ходы берёт
сессия, в которой сидит человек. Комната и запись — те же, что у остальных
агентов, поэтому результат сравним с ними, а не с чужим стеком.

---

## Промпт

> Подключи меня к торговому харнессу Swiftward через почтовый ящик. Значения:
>
> ```
> MAILBOX=https://ХОСТ:8090/mailbox/ТОКЕН
> POLLER=/путь/к/репозиторию/poller
> SESSION_MCP_URL=http://ХОСТ:8081/mcp
> GATEWAY_URL=http://ХОСТ:8082/mcp
> GATEWAY_TOKEN=...
> BROKER_MCP_URL=https://ХОСТ/mcp/alpaca-agent-ИМЯ
> BROKER_MCP_TOKEN=...
> ```
>
> Сделай по порядку.
>
> **1. Проверь ящик до всего остального.** `curl -s $MAILBOX/state` должен
> вернуть JSON с `thread`, `pending`, `running`. Если приходит 404 — токен не тот
> или стенд поднят без `AGENT_DRIVER=mailbox`; дальше не иди, скажи мне.
>
> **2. Подключи три MCP-сервера.** Ровно те же три, что видит агент на codex:
>
> ```sh
> claude mcp add --transport http session $SESSION_MCP_URL
> claude mcp add --transport http gateway $GATEWAY_URL --header "Authorization: Bearer $GATEWAY_TOKEN"
> claude mcp add --transport http broker  $BROKER_MCP_URL --header "Authorization: Bearer $BROKER_MCP_TOKEN"
> ```
>
> Проверь, что все три отвечают списком инструментов. У `broker` их около
> пятидесяти, у `session` — девять, у `gateway` — один.
>
> **3. Заведи монитор.** Persistent, командой:
>
> ```
> $POLLER/poll-stream.sh $MAILBOX
> ```
>
> **`2>&1` не добавляй.** Событием считается только stdout; со слитым stderr
> каждый переподключ и каждый бэкофф станут «ходом», и сессия будет будить себя
> собственной сантехникой.
>
> **4. Запомни, что делать, когда монитор что-то напечатает.** Каждая строка —
> один JSON-объект:
>
> - `{"event":"turn", ...}` — открылось окно расписания или мне написали в
>   комнате. Поле `text` — задача, `turn` — к чему привязывать ответ.
> - `{"event":"steer", ...}` — человек дописал в ход, который уже идёт. Это тот
>   же ход, не новый: учти сказанное и продолжай.
> - `{"event":"interrupt", ...}` — харнесс сдался ждать. Прекрати работу, ответ
>   уже никого не интересует.
>
> На `turn` работай так:
>
> 1. `gateway` → спроси конверт. Пределы приходят оттуда, а не из этого текста.
>    Конверт молчит — не торгуй и скажи об этом; не подставляй число ниоткуда.
> 2. `session` → `read_state`, при надобности `read_schedule`,
>    `read_candidates`, `read_volatility_history`.
> 3. Перед КАЖДОЙ заявкой — `session` → `record_intent`: тезис, конструкция,
>    максимальный убыток. Запись намерения до действия — это то, по чему потом
>    сверяют объявленное с сделанным.
> 4. Заявка — только через `broker` (`place_option_order`). Напрямую в REST
>    Alpaca не ходить ни при каких обстоятельствах: правила площадки требуют MCP
>    или CLI, и шлюз — это то, что отказывает и записывает.
> 5. Отчитайся и закрой ход:
>
> ```sh
> $POLLER/reply.sh $MAILBOX say  "$TURN" "что сделал и почему, одной-двумя фразами"
> $POLLER/reply.sh $MAILBOX done "$TURN"
> ```
>
> `say` — сколько угодно раз, это то, что видят люди в комнате. `done` — ровно
> один раз, когда ход закончен. Ход, который никто не закрыл, держит следующее
> окно закрытым: харнесс считает, что сессия ещё работает.
>
> **5. Правила, которые сильнее твоих привычек.** Своих правил не выдумывай:
> добавленные самопроверкой ограничения перемножаются, и агент перестаёт входить
> вообще, продолжая звучать осторожно. Числа берутся из конверта и из задачи; где
> задача и приём расходятся, сильнее задача. Полный список — `agent/AGENTS.md` в
> репозитории, прочитай его один раз и держись его.
>
> **6. Скажи мне, что получилось**, и покажи первый забранный ход, когда он
> придёт.

## Проверить, что всё встало, не дожидаясь окна

Написать в комнату стенда (Telegram, топик агента) — это тоже причина разбудить
сессию, и она пройдёт тот же путь: ящик → монитор → ответ. Если у стенда нет
чата, можно подождать ближайшего окна расписания или временно добавить в
декларацию сессию с `every: 1m`.

Состояние ящика в любой момент:

```sh
curl -s "$MAILBOX/state"
# {"thread":"mb-…","pending":0,"running":[],"hold":"1m30s","stale":"10m0s"}
```

`pending` больше нуля и растёт — ходы паркуются, а монитор их не берёт: он не
запущен, упал, или его вывод никто не читает. `running` не пустеет — ход не
закрывают через `done`.

## Что не надо делать

**Не запускать два монитора на один токен.** Один ход достаётся одному
поллеру — второй заберёт следующий, и два клиента будут работать вперемешку по
одной идентичности. Нужен второй агент — нужен второй процесс со своим токеном,
своей декларацией и своей базой; в этом стенде так уже и сделано, каждый агент
отдельная служба.

**Не давать `poll-once.sh` монитору.** Он говорит одну вещь и выходит; монитор,
читающий строки, увидит одну и решит, что поток кончился. Мониторам —
`poll-stream.sh`, а `poll-once.sh` тому, что просыпается по выходу процесса.
